== Versions

[[COD-100]]
*COD-100.* Libraries and extensions MUST compile for Java 21, with `maven.compiler.release` set to `21`.
They MUST build and test on the Java 25 long-term support release.
The {abbr-ci-first} SHOULD also test on the latest feature release of the JDK.
That job does not block a merge.
Check: the rules `requireJavaVersion` and `requireProperty` of the Maven Enforcer Plugin, the latter on `maven.compiler.release` with the value `21`.
Review checks the {abbr-ci} jobs.

Java 21 is the floor of Quarkus 4, as the link:https://quarkus.io/blog/quarkus-4-0-0-beta1-released/[Quarkus 4.0.0.Beta1 announcement] states.
Java 25 is the current long-term support release.
The next review of this page checks the next long-term release.

[[COD-101]]
*COD-101.* A published artifact MUST NOT use a preview feature of Java.
Check: a {abbr-ci} search for `--enable-preview` in the build files.

A class file that uses preview features runs only on the exact JDK that compiled it, as link:https://openjdk.org/jeps/12[JEP 12] explains.

== Format and analysis

[[COD-102]]
*COD-102.* Java code MUST follow the formatter settings of the Quarkus project.
The formatter and import sort plugins of Maven apply them.
The {abbr-ci} MUST run the goals `formatter:validate` and `impsort:check`.
Check: those two goals in the Maven build.

The link:https://github.com/quarkusio/quarkus/blob/main/CONTRIBUTING.md[Quarkus contributing guide] formats code in the build and fails {abbr-ci} on any change.
The link:https://hub.quarkiverse.io/checklistfornewprojects/[Quarkiverse checklist] asks the same of new extensions.
An {abbr-fpsot-first} extension can then move to Quarkiverse without a reformat.
The link:https://code.revelc.net/formatter-maven-plugin/[formatter plugin] and the link:https://code.revelc.net/impsort-maven-plugin/[import sort plugin] do the work.

[[COD-103]]
*COD-103.* Each package MUST carry the JSpecify annotation `@NullMarked`, in its `package-info.java` file or on the module.
NullAway MUST run at the error level, with its JSpecify support turned on.
Check: NullAway, through Error Prone, at compile time.

The link:https://jspecify.dev/docs/user-guide/[JSpecify user guide] makes each unannotated type non-null inside `@NullMarked` code.
Packages do not nest, so each package needs its own annotation.
Kotlin reads these annotations, so a Kotlin caller gets types that cannot hold `null`.
link:https://github.com/uber/NullAway/releases[NullAway] checks them during the build.

[[COD-104]]
*COD-104.* The Maven build MUST run Error Prone and SpotBugs with the Find Security Bugs plugin.
Its tests MUST include ArchUnit tests of the package rules of COD-114.
A project MAY add Checkstyle, but the formatter of COD-102 owns the layout.
Check: the Maven build.

link:https://github.com/google/error-prone/releases[Error Prone] runs inside the compiler.
link:https://spotbugs.github.io/[SpotBugs] reads the bytecode, and link:https://find-sec-bugs.github.io/[Find Security Bugs] adds security detectors to it.
link:https://www.archunit.org/[ArchUnit] states rules on packages and classes as unit tests.
TST-006 leaves the test runner open, and Java projects use JUnit Jupiter.
Limits on the length of methods or the number of parameters stay review guidance, not build failures.

== Errors and data

[[COD-105]]
*COD-105.* An expected business outcome, such as a refusal, MUST be a value of a sealed type.
The caller MUST handle it with a `switch` that covers each permitted type.
Exceptions MUST extend `RuntimeException`, and MUST serve bugs and failures of the infrastructure only.
Code that wraps an exception MUST pass the original as its cause.
Check: review.

link:https://openjdk.org/jeps/409[Sealed classes], link:https://openjdk.org/jeps/395[records], link:https://openjdk.org/jeps/440[record patterns] and link:https://openjdk.org/jeps/441[pattern matching for switch] let the compiler check that the caller handles each case.
The Java binding of the decisions specification uses the same shape, under DEC-021.
Kotlin follows the same model, under COD-303.

[[COD-106]]
*COD-106.* A method MUST NOT return `null` in place of an empty collection or an empty `Optional`.
Code MUST NOT use Java serialization to exchange or store data.
Check: NullAway for `null` returns in code that `@NullMarked` covers, and Find Security Bugs for unsafe deserialization.
Review covers the rest.

== Build

[[COD-107]]
*COD-107.* Java and Quarkus projects MUST build with Maven, through the Maven Wrapper.
The wrapper properties MUST give the checksum of the Maven distribution in `distributionSha256Sum`.
Gradle is allowed only for Kotlin Multiplatform modules, under COD-304.
Check: review.

The tools of Quarkus extensions and of Quarkiverse assume Maven.
The link:https://maven.apache.org/wrapper/[Maven Wrapper] downloads one Maven version and checks it against the committed checksum.

[[COD-108]]
*COD-108.* The build MUST fix the version of each dependency in `dependencyManagement` or through an imported bill of materials.
It MUST pin the version of each plugin.
The Maven Enforcer Plugin MUST run these rules: `requireMavenVersion`, `requireJavaVersion`, `requirePluginVersions`, `dependencyConvergence` and `banDynamicVersions`.
Check: the link:https://maven.apache.org/enforcer/[Maven Enforcer Plugin].

This is how a Maven build meets SEC-030 without a lock file.
The file `examples/maven-enforcer.xml` shows the rules.
The link:https://maven.apache.org/enforcer/enforcer-rules/index.html[list of built-in rules] describes each one.

[[COD-109]]
*COD-109.* The build MUST set `project.build.outputTimestamp`.
The release workflow MUST rebuild each release and compare it with the published files, with the goal `artifact:compare`.
It MUST publish the `.buildinfo` file next to the artifacts.
Check: the release workflow.

The link:https://maven.apache.org/guides/mini/guide-reproducible-builds.html[Maven guide on reproducible builds] says that Maven 3.10.0 turns on the reproducible mode by default.
The output depends on the major version of the JDK, so the release workflow pins it.
This rule meets COD-022.

[[COD-110]]
*COD-110.* Each published library MUST pass a check of its public interface against its last release, with japicmp or Revapi.
A change that breaks a caller MUST fail the build unless the major version changes.
Check: the link:https://github.com/siom79/japicmp[japicmp] Maven plugin in {abbr-ci}.

Release tags follow Semantic Versioning, under VCS-106.
This check turns that promise into a test.

[[COD-111]]
*COD-111.* Each library without a `module-info.java` file MUST set `Automatic-Module-Name` in the manifest of its archive.
The name SHOULD follow NAM-022, which is itself a SHOULD.
Check: review of the archive manifest.

[[COD-112]]
*COD-112.* Code MUST NOT pool virtual threads.
It SHOULD put an explicit limit on each scarce resource that they use.
A semaphore or the size of a connection pool sets such a limit.
Check: review.

link:https://openjdk.org/jeps/444[JEP 444] presents virtual threads as cheap, and advises against pooling them.
Since link:https://openjdk.org/jeps/491[JEP 491] in JDK 24, a `synchronized` block no longer pins a virtual thread to its carrier.
This page builds on Java 25, so it keeps no rule against `synchronized`.

[[COD-113]]
*COD-113.* A release to Maven Central MUST meet the link:https://central.sonatype.org/publish/requirements/[requirements of the Central Publisher Portal].
Each artifact needs a signature, a sources archive and a Javadoc archive.
The project model needs a name, a description, a web address, the licenses, the developers and the source repository.
Check: the Central Publisher Portal checks each upload.

The link:https://central.sonatype.org/publish/publish-maven/[guide for Maven] gives the plugin to use.

== Packages

[[COD-114]]
*COD-114.* An {abbr-fpsot} library MUST keep its domain and its ports apart from its adapters.
Their packages MUST NOT import an adapter package.
Adapters MUST depend on ports, never the reverse.
An application module MAY use layered packages inside its adapters.
Check: an ArchUnit test, under COD-104.

A port is the plain Java interface that an adopter can replace.
The xref:overridable-rules.adoc[Overridable rules] page shows how a Quarkus extension exposes one.
