= PowerShell
include::_fpsot-terms.adoc[]

Cette page vise les scripts et les modules PowerShell.
Les organismes publics exploitent de nombreux hôtes Windows.
La {abbr-fpsot-first} a besoin de PowerShell pour y installer et y exploiter des logiciels.

== Outils de l’édition 2026

[cols="2,1,3",options="header"]
|===
|Outil |Version |Rôle
|PowerShell |7.6, à soutien à long terme |Exécute les scripts sur tout système.
|Windows PowerShell |5.1 |Exécute les scripts sur les hôtes Windows qui n’ont rien de plus récent.
|PSScriptAnalyzer |1.25.0 |Analyse et met en forme les scripts.
|Pester |6.2.0 |Teste les scripts.
|===

Le link:https://learn.microsoft.com/en-us/powershell/scripting/install/powershell-support-lifecycle?view=powershell-7.6[cycle de vie du support de PowerShell] prévoit le support de la version 7.6 jusqu’au 2028-11-14.
Windows PowerShell 5.1 est livré avec Windows et suit son cycle de vie.

== Règles

[[COD-550]]
*COD-550.* Chaque script et chaque module DOIT déclarer la version dont il a besoin.
Il le fait avec `#Requires -Version 5.1` ou `#Requires -Version 7.6`.
L’{abbr-ci-first} DOIT le tester sur chaque édition qu’il déclare.
Un script pour la version 5.1 s’exécute aussi sous 7.6, alors l’{abbr-ci} le teste sur les deux.
Vérification : revue des tâches de l’{abbr-ci}.

[[COD-551]]
*COD-551.* Chaque {term-repository} DOIT analyser ses scripts avec PSScriptAnalyzer et un fichier de paramètres archivé.
Les paramètres DOIVENT activer les règles de mise en forme, désactivées par défaut.
Ils DOIVENT aussi activer `PSUseCompatibleSyntax`, avec les cibles `'5.1'` et `'7.0'`.
Vérification : `Invoke-ScriptAnalyzer` avec ce fichier de paramètres dans l’{abbr-ci}.

La link:https://learn.microsoft.com/en-us/powershell/utility-modules/psscriptanalyzer/rules/readme?view=ps-modules[liste des règles de PSScriptAnalyzer] indique celles qui sont désactivées par défaut.
Le link:https://learn.microsoft.com/en-us/powershell/utility-modules/psscriptanalyzer/using-scriptanalyzer?view=ps-modules[guide de PSScriptAnalyzer] décrit le fichier de paramètres.
Le fichier `examples/PSScriptAnalyzerSettings.psd1` en montre un.
La règle accepte les versions majeures 3 à 7.
La cible `'7.0'` représente donc la syntaxe de PowerShell 7.

[[COD-552]]
*COD-552.* Les scripts DOIVENT n’employer que des verbes approuvés dans les noms de fonctions.
Ils DOIVENT employer le nom complet des commandes plutôt que des alias.
Ils DOIVENT passer les paramètres par leur nom.
Ils NE DOIVENT PAS appeler `Invoke-Expression`, ni contenir un mot de passe ou une clé en clair.
Vérification : les règles par défaut de PSScriptAnalyzer, comme `PSUseApprovedVerbs` et `PSAvoidUsingInvokeExpression`, et la revue.

La link:https://learn.microsoft.com/en-us/powershell/scripting/developer/cmdlet/approved-verbs-for-windows-powershell-commands?view=powershell-7.5[liste des verbes approuvés] vient de Microsoft.

[[COD-553]]
*COD-553.* Un module DOIT exporter ses fonctions par leur nom explicite, jamais avec un caractère générique.
Il NE DOIT PAS charger des fichiers de script par dot-sourcing.
Vérification : les règles `PSUseConstrainedLanguageMode` et `PSUseToExportFieldsInManifest`, ou la revue.

Sous App Control for Business, PowerShell exécute les scripts non approuvés en mode de langage restreint.
Le link:https://learn.microsoft.com/en-us/powershell/scripting/security/app-control/how-app-control-works?view=powershell-7.5[guide de Microsoft sur App Control] demande aux modules d’éviter le dot-sourcing et les exportations génériques.

[[COD-554]]
*COD-554.* Chaque script et chaque module publié DOIT porter une signature Authenticode.
Les guides d’installation NE DOIVENT PAS dire aux utilisateurs de régler la stratégie d’exécution à `Bypass` pour tout l’ordinateur.
Vérification : revue du flux de publication et des guides.

La link:https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies?view=powershell-7.5[documentation des stratégies d’exécution] précise que la stratégie n’est pas une frontière de sécurité.
Une signature, décrite dans link:https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_signing?view=powershell-7.5[about_Signing], permet à un hôte de faire confiance au script.

[[COD-555]]
*COD-555.* Chaque fonction DOIT déclarer `[CmdletBinding()]`, ce qui en fait une fonction avancée.
Le code qui traite une erreur DOIT employer `try` et `catch`, avec `-ErrorAction Stop` sur la commande.
Un bloc `catch` NE DOIT PAS être vide.
Vérification : PSScriptAnalyzer, avec `PSAvoidUsingEmptyCatchBlock`, et la revue.

[[COD-556]]
*COD-556.* Un script destiné à des hôtes sous App Control DEVRAIT passer la règle `PSUseConstrainedLanguageMode`.
Vérification : PSScriptAnalyzer, avec cette règle activée.

[[COD-557]]
*COD-557.* Les scripts et les modules DEVRAIENT avoir des tests link:https://github.com/pester/Pester/releases[Pester], exécutés dans l’{abbr-ci} sur chaque édition déclarée.
Vérification : revue.

[[COD-558]]
*COD-558.* Un script DEVRAIT lire les secrets au moyen du module SecretManagement, jamais dans un fichier du {term-repository}.
Vérification : revue, et l’analyse des secrets de SEC-013.

Cette règle reste une recommandation, car la dernière version de SecretManagement date de 2022.
Le responsable de cette page vérifie son entretien à chaque révision.

Le guide communautaire link:https://poshcode.gitbook.io/powershell-practice-and-style[PowerShell Practice and Style] donne d’autres conseils.
Sa licence exige que les copies soient partagées dans les mêmes conditions.
Cette page se limite donc à en résumer des idées.
