== Règles

[[COD-500]]
*COD-500.* Un script exécutable DOIT commencer par `#!/usr/bin/env bash` et viser Bash 4.4 ou une version plus récente.
Un script PEUT employer le `sh` de POSIX seulement là où son environnement n’a pas Bash.
C’est le cas, par exemple, d’une image de conteneur minimale.
Vérification : ShellCheck, qui lit le shell sur la première ligne.

Le link:https://google.github.io/styleguide/shellguide.html[guide de style shell de Google] sert de guide de style à cette page.

[[COD-501]]
*COD-501.* Chaque script DOIT passer ShellCheck à son niveau de gravité par défaut.
Il DOIT passer `shfmt -d` avec un retrait de 2 espaces, fixé dans `.editorconfig`.
Vérification : link:https://github.com/koalaman/shellcheck/releases[ShellCheck] et link:https://github.com/mvdan/sh/releases[shfmt] dans l’{abbr-ci}.

[[COD-502]]
*COD-502.* Un script DOIT mettre entre guillemets chaque variable et chaque substitution de commande qu’il développe.
Il DOIT transmettre les arguments avec `"$@"`, faire ses tests avec `[[ ]]` et capter les sorties avec `$( )`.
Il NE DOIT PAS employer `eval`.
Le {term-repository} DOIT archiver à sa racine un fichier `.shellcheckrc` qui contient `enable=require-double-brackets`.
Vérification : ShellCheck avec ce fichier, et une recherche de `eval` dans chaque script par l’{abbr-ci}.

La vérification facultative `require-double-brackets` de ShellCheck signale chaque test `[ ]` dans un script Bash.
Le fichier `examples/.shellcheckrc` montre ce réglage.

[[COD-503]]
*COD-503.* Un script DEVRAIT commencer par `set -Eeuo pipefail` et `shopt -s inherit_errexit`.
Il DOIT tout de même vérifier le résultat de chaque commande critique.
Il DOIT écrire ses erreurs sur la sortie d’erreur standard.
Vérification : revue.

Ces options arrêtent bien des erreurs, mais pas toutes.
L’link:https://mywiki.wooledge.org/BashFAQ/105[entrée de la BashFAQ sur errexit] énumère les cas où une commande en échec n’arrête pas le script.
Une condition, une affectation `local` et certains sous-shells en font partie.

[[COD-504]]
*COD-504.* Un script DOIT créer ses fichiers et dossiers temporaires avec `mktemp`.
Il DOIT les supprimer dans un `trap` sur `EXIT`.
Il NE DOIT PAS employer un chemin fixe pour ses données temporaires.
Vérification : revue.

[[COD-505]]
*COD-505.* Un script de plus de 100 lignes DOIT devenir un programme Go, selon la page xref:go.adoc[Go].
Un script qui analyse des données structurées, comme du {abbr-json-first} ou du {abbr-xml-first}, DOIT aussi en devenir un.
Vérification : un contrôle par l’{abbr-ci} que `wc -l` donne 100 ou moins pour chaque script.
La revue vérifie l’analyse des données.

Le guide de Google fixe une limite d’environ 100 lignes.
Un programme Go profite des types, des tests et des mêmes analyseurs statiques que les autres outils de la {abbr-fpsot-first}.

[[COD-506]]
*COD-506.* Un script dont dépend un autre code DEVRAIT avoir des tests link:https://github.com/bats-core/bats-core/releases[bats-core], exécutés dans l’{abbr-ci}.
Vérification : revue.

Depuis la version 1.14, la commande `run` de bats respecte `set -e`, ce qui peut briser d’anciens tests.
