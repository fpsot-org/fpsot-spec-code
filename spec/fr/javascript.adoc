= JavaScript et TypeScript
include::_fpsot-terms.adoc[]

Cette page vise JavaScript et TypeScript, dans le navigateur et dans les outils Node.js.
L’interface de la {abbr-fpsot-first} produit le {abbr-html-first} sur le serveur.
Les scripts enrichissent donc des pages qui fonctionnent déjà.

La révision vient après six mois, car TypeScript et son analyseur statique sont entre deux versions majeures.

== Règles

[[COD-600]]
*COD-600.* Tout nouveau travail DOIT s’exécuter sur Node.js 26.
Un projet DOIT s’exécuter seulement sur une branche de Node.js en soutien à long terme, active ou en maintenance.
Il DOIT déclarer cette branche dans le champ `engines` de `package.json` et dans un fichier `.node-version`.
Vérification : `npm ci`, qui avertit d’un moteur incorrect, et revue des tâches de l’{abbr-ci-first}.

La link:https://nodejs.org/en/about/previous-releases[page des versions de Node.js] donne chaque branche et sa date de fin.
À partir de Node.js 27, il paraît link:https://nodejs.org/en/blog/announcements/evolving-the-nodejs-release-schedule[une version majeure par an].
Chacune devient une version à soutien à long terme.

[[COD-601]]
*COD-601.* Un projet DOIT vérifier les types et analyser le code avec TypeScript 6.0.x.
Cette règle vaut tant que typescript-eslint ne prend pas en charge TypeScript 7.
Il PEUT aussi compiler avec TypeScript 7.
Vérification : la version de `typescript` dans le fichier de verrouillage, et la revue.

link:https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/[TypeScript 7.0] est un portage natif, paru sans interface pour les autres outils.
Les link:https://typescript-eslint.io/users/dependency-versions/[versions prises en charge par typescript-eslint] s’arrêtent avant TypeScript 6.1.
Les règles qui lisent les types comptent plus que la vitesse du compilateur, alors l’analyseur statique l’emporte.
Le responsable revoit cette règle quand typescript-eslint prendra en charge TypeScript 7.

[[COD-602]]
*COD-602.* Le fichier `tsconfig.json` DOIT activer `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride` et `verbatimModuleSyntax`.
Le code DOIT employer uniquement des modules ECMAScript.
Vérification : le compilateur, et la revue de `tsconfig.json`.

La link:https://www.typescriptlang.org/tsconfig/[référence TSConfig] décrit chaque option.
Le code que Node.js exécute sans étape de construction a aussi besoin de `erasableSyntaxOnly`.

[[COD-603]]
*COD-603.* ESLint DOIT analyser le code avec une configuration plate et l’ensemble `strictTypeChecked` de typescript-eslint.
Le plugiciel de commentaires d’ESLint DOIT activer sa règle `require-description`, selon COD-010.
Prettier DOIT mettre en forme le code.
Vérification : `eslint` et `prettier --check` dans l’{abbr-ci}.

link:https://eslint.org/docs/latest/use/migrate-to-10.0.0[ESLint 10] ne lit plus l’ancien format de configuration.
Les link:https://typescript-eslint.io/users/configs/[configurations partagées de typescript-eslint] comprennent `strictTypeChecked`.
link:https://prettier.io/[Prettier] décide de la mise en page.
Le fichier `examples/eslint.config.mjs` montre une configuration conforme.

[[COD-604]]
*COD-604.* Un projet DOIT versionner son fichier de verrouillage et installer avec `npm ci`.
Son fichier `.npmrc` DOIT régler `ignore-scripts=true` et `allow-git=none`.
Il DOIT aussi régler `min-release-age` à au moins 3 jours.
Vérification : revue de `.npmrc` et des tâches de l’{abbr-ci}.

Ces link:https://docs.npmjs.com/cli/v11/using-npm/config[paramètres de npm] sont le mécanisme de npm pour SEC-030 et SEC-032.
Un délai d’attente laisse au registre le temps de retirer une version malveillante avant qu’un projet l’installe.

[[COD-605]]
*COD-605.* Un projet qui publie un paquet sur npm DOIT le publier par publication de confiance, avec sa provenance.
Vérification : le flux de publication.

La link:https://docs.npmjs.com/trusted-publishers/[publication de confiance] emploie une identité de courte durée fournie par l’{abbr-ci}, au lieu d’un jeton conservé.
Elle ajoute la provenance d’elle-même.
Elle sert SEC-024 et SEC-035.

[[COD-606]]
*COD-606.* Une interface DOIT produire ses pages en {abbr-html} sur le serveur, et ajouter les scripts par amélioration progressive.
Un projet qui a besoin d’un cadriciel d’application monopage DOIT d’abord consigner cette décision, avec ses motifs.
Vérification : revue.

Le link:https://www.gov.uk/service-manual/technology/using-progressive-enhancement[GOV.UK Service Manual] explique pourquoi les pages devraient fonctionner avant le chargement des scripts.
La pile par défaut de la {abbr-fpsot} réunit des gabarits Qute, PatternFly, HTMX et Alpine.js.

[[COD-607]]
*COD-607.* Le code DOIT garder les données à clés venues de l’extérieur dans une `Map` ou un `Set`.
Il NE DOIT PAS employer un objet ordinaire comme dictionnaire pour de telles données.
Il NE DOIT PAS copier des clés venues de l’extérieur dans un objet ordinaire sans liste d’autorisation.
Vérification : revue.

Cette règle suit l’exigence 15.3.6 de l’{abbr-owasp-first} {abbr-asvs-first}, qui demande au code d’empêcher la pollution de prototype.
